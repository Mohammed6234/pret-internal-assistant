# Access-Control and Permission-Aware RAG Prototype Design

## Objective

Replace the current end-to-end assistant implementation with one small, defensible pro-code slice that demonstrates exactly two consecutive architecture blocks:

`Access control → Permission-aware retrieval and grounded response`

The prototype must be easy to run, easy to explain, and small enough to change during the interview. It must not imply that it implements Copilot Studio, production orchestration, a live model, a system-of-record action, monitoring, or a real human-support integration.

## Why this scope matches the exercise

The Candidate Exercise asks for one meaningful working slice and explicitly warns against building everything. Access control followed by permission-aware retrieval is meaningful because it demonstrates both an important security boundary and an AI grounding fundamental. The rest of the architecture remains presentation material rather than repository code.

## Technology choice

Use Python 3.11 or later and Streamlit.

Streamlit is chosen because it provides a credible browser-based chatbot demonstration with very little UI code. The backend remains deterministic and credential-free so the live demonstration is reproducible. Retrieval uses a small local knowledge fixture and explicit metadata matching; the returned answer is stored with the approved document rather than generated by a live language model.

Production equivalents can be discussed without being implemented:

- Entra identity claims replace the role selector.
- Azure AI Search or Copilot Studio native knowledge replaces local retrieval.
- SharePoint or Dataverse replaces the JSON fixture.
- Azure OpenAI may generate a response from the permitted evidence after this slice, but is deliberately outside the prototype.

## User interface

The Streamlit page contains:

1. A title and one-sentence explanation of the prototype.
2. A role selector with `Store colleague` and `Store manager`.
3. Five suggested-question buttons.
4. A chat input that accepts any question.
5. A response panel for one of the three outcomes.
6. A read-only agent case preview shown only after an unsupported question and an explicit `Talk to an agent` click.

The five suggested questions are:

1. `How do I report a faulty display fridge?`
2. `What are the escalation thresholds for repeated equipment faults?`
3. `How do I report that I cannot attend a shift?`
4. `What checks are required when opening the store?`
5. `What is the approved supplier invoice process?`

The second question is manager-only. The fifth question is deliberately unsupported.

## Knowledge fixture

Each entry in `data/knowledge.json` contains:

```json
{
  "id": "OPS-001",
  "title": "Faulty equipment reporting",
  "answer": "Approved, synthetic guidance shown to the user.",
  "url": "https://pret.example/documents/OPS-001",
  "keywords": ["faulty", "fridge", "equipment", "maintenance"],
  "roles": ["Store colleague", "Store manager"]
}
```

The links and guidance are clearly labelled as synthetic demonstration data. No real Pret policy or confidential content is included.

## Backend design

`assistant.py` owns the complete backend slice. It defines small immutable data structures for a document, a result, and an agent case, plus one public function:

```python
answer_question(question: str, role: str, documents: list[Document]) -> Result
```

The function performs these steps in order:

1. Normalize and tokenize the question.
2. Match the question against non-sensitive document metadata: title and keywords.
3. If no document has a meaningful match, return `unavailable` with a prepared agent case.
4. If a document matches, check whether the selected role is included in its `roles` metadata.
5. If access is denied, return `access_denied` without the document answer, ID, URL, or other restricted content.
6. If access is allowed, retrieve the stored answer and return `answer` with the document ID and URL.

Matching metadata before content access lets the prototype distinguish “relevant information exists but you cannot access it” from “no relevant information is available” without exposing restricted document content. In production, the equivalent would be a security-trimmed index or a safe metadata catalogue backed by Entra claims.

## Role-dependent outcomes

### Permitted answer

Both roles may access general documents. The result contains:

- The stored grounded answer.
- The document ID.
- The synthetic document link.

### Access denied

A `Store colleague` asking the repeated-fault escalation question receives exactly:

`Sorry, you do not have the correct access level. Ask your manager to make this request.`

A `Store manager` asking the same question receives the grounded answer, document ID, and link.

The access-denied result must not reveal the restricted answer, document ID, URL, or snippets.

### Information unavailable

If no document matches, the user receives:

`I don't have this information available. Would you like to talk to an agent?`

The result includes a prepared but not submitted case containing:

- A deterministic display reference derived from the question and role.
- The original question.
- The selected role.
- The search outcome: `No approved document matched`.
- The number of document metadata records checked.
- The handoff reason: `Approved information unavailable`.

The Streamlit UI displays the case only after the user clicks `Talk to an agent`. No case is persisted or sent anywhere.

## Error handling

- An empty question returns `unavailable` with a concise request to enter a question; it does not create an agent case.
- An unknown role is rejected with `ValueError` because identity values must come from a trusted, allowlisted source.
- An unreadable or malformed knowledge file stops application startup with a clear error rather than silently returning weak answers.
- Ties between documents are resolved deterministically by score and then document ID.

## Testing

Use the Python standard-library `unittest` module. Tests cover observable behaviour rather than Streamlit internals:

1. A general equipment question returns an answer, document ID, and URL for a store colleague.
2. A general question also works for a store manager.
3. A store colleague is denied the manager-only document.
4. The denied response leaks none of the restricted document fields.
5. A store manager receives the manager-only answer and source.
6. An unsupported invoice question returns `unavailable` and a complete agent case.
7. An empty question asks for input without preparing a case.
8. An unknown role raises `ValueError`.
9. Matching and tie-breaking are deterministic.

## Explicit non-goals

The repository does not implement:

- Copilot Studio or Teams integration.
- Prompt-injection or safety classification.
- A live language model or prompt design.
- Tool calling or state-changing actions.
- Power Automate, Azure Functions, or Foundry orchestration.
- A real support ticket or human-agent integration.
- Authentication, Entra, persistent sessions, telemetry, deployment, CI/CD, or incident handling.
- A broad evaluation framework.

These remain part of the architecture discussion. Excluding them is the central scoping decision demonstrated by the prototype.

## Acceptance criteria

- The final interviewer-facing repository contains only the six agreed application files, the existing `.gitignore`, and normal Git metadata; development-only design and plan documents are removed during final cleanup.
- The UI accepts arbitrary questions and provides five clickable suggestions.
- Switching the role changes the outcome of the manager-only question.
- Allowed answers include a document ID and link.
- Restricted answers reveal no restricted source details.
- Unsupported questions offer a human handoff and show the complete case preview only after confirmation.
- The backend implements only access control and permission-aware retrieval/grounded response.
- All tests pass using one documented command.
- The app runs locally using one documented command and no cloud credentials.
